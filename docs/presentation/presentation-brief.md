## 二、各部分內容規劃

### 0. 封面
- 題目（草案，可改）：**以 AI 規範與多角色分工開發購物網站——前後端分離的實驗**
- 姓名：＿＿＿　學號：＿＿＿　座號：＿＿＿　組別：＿＿＿　（人填寫）

### 1. Introduction（背景與目標）
- 背景：AI 寫程式很快，但「寫得快不等於寫得對」（Vibe Coding 的限制：需求不完整、無人把關、無版本控制、難以維護與上線）
- 研究問題：**使用專業的 AI 規範，能不能做出更完美、更好的購物網站？**
- 專案簡介：購物網站（前後端分離）有哪些功能、給誰用
- 目標與範圍：第一版做什麼、不做什麼（來自 Epic 的「範圍」）
- 老師的要求：我們會修改的前端項目（來自 `frontend-changes.md`）

### 2. The Method（方法）
- 方法來源：課程《Agentic Coding 與 CI/CD》（講師：張竟烜），由具三十年業界經驗的實務工作者提供的新型 AI 開發方法
- 核心做法（每一項在簡報中用一張圖或一張表說明）：
  1. **AGENTS.md**：寫給 AI 看的專案規範（活文件）
  2. **多角色 Subagent**：11 個角色（PO、Scrum Master、System Analyst、UI/UX、DBA、前端、後端、Tester，以及三種唯讀審查者）
  3. **Scrum 三層節奏**：Epic → Story → Task；DoR／DoD
  4. **Pull Request＋CI**：自動檢查，合併由人決定
  5. **人把關**：需求、規則、金錢、合併、佈署由人決定
- 本專案的架構決定：**前後端分離**，以 API 契約（OpenAPI）溝通；前端可用 Mock 獨立運行

### 3. Its application（方法的應用）
- 方法如何套到購物網站：
  - 架構圖：前端（Vue）⇄ API 契約 ⇄ 後端（FastAPI）⇄ 資料庫
  - 一個需求從頭到尾怎麼走（例：「加入購物車」）：Story → 契約 → 前後端 Task → PR → CI → 審查 → 人合併
  - 各角色實際做了什麼（取自各 Sprint 的紀錄）
  - **前端手動修改機制**：手動修改區、修改登記、不覆蓋人的修改
  - 購物網站特有的規則：庫存、訂單狀態機、金額、付款安全
  - 程式碼備註與程式碼導覽（`docs/code-guide.md`）如何幫助我們看懂程式

### 4. Run examples, get the results and discussion（執行範例、結果與討論）
**(a) 現場示範（建議用 `npm run dev:mock`，不需後端也能展示）**
- 主要流程：找商品 → 加入購物車 → 結帳 → 查詢訂單
- 手動修改前端的 Before／After：改設定檔或樣式，畫面立即變化

**(b) 結果（數據來自實際輸出，記錄於 `results-log.md`）**
| 指標 | 說明 |
|---|---|
| 完成的 Epic／Story／Task 數 | 做了多少 |
| 測試數量與覆蓋率（前後端） | 品質證據 |
| CI 通過／失敗次數與原因 | 自動檢查有沒有抓到問題 |
| 三種審查發現的問題數 | Code／Security／QA 抓到什麼 |
| 人介入的決定次數與內容 | 人到底決定了哪些事 |
| Agent 主動提出的待決事項 | AI 有沒有亂猜 |
| 新增進 AGENTS.md 的規則數 | 方法是否越用越好 |
| 前端手動修改次數、是否弄壞 build | 手改的安全性 |

**(c) 對照（可選，需人決定）**：同一個小功能（例如商品列表＋購物車），分別用「單一 Prompt（Vibe Coding）」與「AI 規範流程」各做一次，比較結果。

**(d) 討論（誠實面對）**
- 哪些地方 AI 規範明顯有幫助？（例：不亂猜、可追溯、有測試）
- 哪些地方變慢或變麻煩？（例：前置文件多、需要人一直決定）
- 遇到哪些問題、怎麼解決？（來自 AGENTS.md 第 9 章變更紀錄）
- AI 的限制，以及人不能交出去的工作
- **能不能做出「更完美」的東西？**——用數據回答，不誇大

### 5. Conclusion（結論）
- 回答研究問題（有／部分有／沒有，並說明依據）
- 方法的優點、限制與風險
- 未來改進（例：自動串接專案管理、更完整的 E2E 測試、正式佈署）
- 我們學到的事
